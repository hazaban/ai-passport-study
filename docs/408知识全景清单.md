## 0. 系统全景

### 0.1 设备到底是谁
一台自带屏、3 键、麦克风/喇叭的学习提醒机器。内部芯片是 **ESP32-C3**：
- CPU：RISC-V 单核，`RV32IMC`，160MHz，**无 FPU**
- 内存：SRAM 约 400KB（系统把手脚快、但容量小）
- 存储：4MB SPI Flash（代码 + 音频 + 用户数据全在这）
- 外设：I2S（音频）、SPI（LCD 屏）、I2C、ADC（按键/电池）、GPIO
- 无线：WiFi 2.4GHz + 蓝牙 BLE

### 0.2 层次化结构（408 第一题常客）
```
应用：Study 考研助手（任务/提醒/录音/UI）
中间件：LVGL、Speex/Opus、SPIFFS、NVS、esp-timer、WiFi/LwIP、httpd
内核：FreeRTOS（任务/调度/栈/信号量/队列）
BSP：bsp_i2c/bsp_audio/bsp_button/bsp_display/bsp_battery
硬件：RISC-V + SRAM + Flash + 屏 + 麦克风 + 天线
```
**结论**：这就是"计算机系统由**硬件+系统软件+应用软件**自底向上组成"的活例。

# 第一部分　计算机组成原理

> 对应 408《计算机组成原理》大纲。本项目把"读写文件、按个键、上网"这些应用层动作，
> 一路拆到**寄存器/总线/闪存页**——正是计组要你理解的东西。

## 1.1 计算机系统概述 & 性能
- **多级存储结构** → §1.3 存储系统有全程实例
- **性能指标**：CPU 主频 160MHz；Flash 4MB；采样"数据量 = 采样率×位宽×声道×时间"（`8k×16×1×20ms=2560B/帧`），是吞吐带宽计算的题源

## 1.2 数据的表示和运算（408 大纲重点）
- **进制与换算**：分区表偏移 `0x9000=36864`、`0x300000=3MB`、`0x32E000≈3.05MB`——十六/十/二互换题源源不绝
- **定点数与补码**：录音 PCM 用 `int16_t`（范围 `[-2^15,2^15-1]`，`-1=0xFFFF`）。无 FPU → Speex 全用 `FIXED_POINT` 定点（Q 格式），"实数值存成整数×缩放系数"
- **溢出**：帧数 `frames*20 > REC_MAX_SEC*1000` 用 `uint32_t` 防溢出；`data_bytes=frames*320*2` 同理
- **大小端**：FRC 用 `u16LE` 存帧长；WAV 头 `put_u32le` 把小端整型**逐字节**写入。RISC-V/x86 均小端，但与网络字节序（大端）打交道必须 `htonl/ntohl`
- **位运算**：`repeat` 的 `bit0~bit6` 每周七天；`frames%50`（模运算）；状态位 `&/|`

## 1.3 存储系统（★含"文件IO流"之一半）
### 1.3.1 存储层次 + 每层落在哪
| 层次 | 本设备对应 | 特点 |
|---|---|---|
| 寄存器 | RV32 32 个通用寄存器 | CPU 内、最快、容量最小 |
| SRAM（主存） | 400KB：`.data/.bss/.rodata`+堆+栈 | 掉电丢失、按字节/字访问 |
| Flash（外存） | 4MB：代码+SPIFFS 数据区 | 持久、按**扇区/页**擦写、读快写慢 |
| 分区表 | 固定地址映射 | 见下 |

### 1.3.2 地址空间与分区表（内存地址分配最直接案例）
```csv
nvs,        data, nvs,     0x9000,   0x6000,      # 系统参数键值
phy_init,   data, phy,     0xf000,   0x1000,      # 电台校准
factory,    app,  factory, 0x10000,  0x300000,    # 固件3MB
cardid,     data, nvs,     0x356000, 0x4000,      # 安装器固定
voicepack,  data, spiffs,  0x35A000, 0x78000,     # 语音包480KB
recordings, data, spiffs,  0x3D2000, 0x32E000,    # 录音≈3.05MB
recovery,   app,  test,    0x700000, 0x100000,    # 恢复1MB
```
- 换算练习：`0x10000`=64KB；`0x10000+0x300000=0x310000`；末尾 `0x700000+0x100000=0x800000`=4MB 上限
- **计组考点**：
  - **静态地址映射**：每次复位地址固定 → 引导程序（bootloader）到 `0x10000` 找 factory，即"上电入口地址"机制
  - **Flash/ROM 只读，SRAM 读写**：`const` 常量表/码本被链进 Flash（地址 `0x42000000` MMU 窗）；可写全局变量在 DRAM。这就是 `.rodata vs .data/.bss` 分段
  - **Cache/MMU**：ESP32-C3 的 I-Cache/D-Cache + Flash MMU 负责"按需把 Flash 中的代码/常量映射到可执行窗口"——类比计组 Cache 读未命中才去访存

### 1.3.3 SRAM 内部：堆 vs 栈（一段都在计组/OS 交叉）
- `.text/.rodata`、`.data（已初始化全局）`、`.bss（零初始化）`、堆（`malloc` 动态区）、各任务**独立栈**
- 堆向上长、栈向下长，两者相向 → 相碰 = 堆损坏/栈溢出（本项目 16kHz 崩溃根因，见第 6 章）

## 1.4 指令系统（RV32IMC）
- **RISC vs CISC**：RISC-V 是典型 RISC（少而规整指令、Load/Store 架构）
- **Load/Store 架构**：算术必须在寄存器里做，访问内存只有 `lw/sw/lb/sb` 等装入/存储指令 → Speex 大量局部变量尽量进寄存器，省内存访问
- **扩展位**：`IMC` = 整数 + 乘除 + 压缩指令。`M` 让乘除法一条指令完成（`m/div`）；`C` 16 位短指令提高代码密度、省 Flash
- **寻址方式**：立即数、寄存器、基址+偏移（数组 `buf[i]` → 基地址 + i×偏移）

## 1.5 中央处理器与中断（★"点击按钮触发中断"之一半）
**中断四要素（408 必背）**：中断源 → 中断请求 → 中断响应 → 中断服务/返回。
本项目两个层次的中断都在用：

### 1.5.1 真正的硬件中断
- **定时器中断**：`esp_timer` 底层由硬件定时器产生**周期性中断**，用来"每 100ms 扫一次按键电压"、"每秒写一次诊断日志"。这就是"由定时器中断驱动的周期性任务"
- **DMA 中断**：I2S 音频帧到齐触发 DMA，DMA 完成后可中断 CPU 消费数据（录音循环 `bsp_audio_read` 拿到新样本的源）
- **WiFi/BLE**：射频收发完成产生中断 → 协议栈处理 → 通过**事件**通知上层（`on_wifi_event`）

### 1.5.2 按键的"准中断"链路（讲清真实机制）
按键引脚是 **ADC 采样轮询**，不是硬中断引脚。完整链路：
```
物理按压 → ADC分压电压变化
  → 定时器中断每 ~10ms 触发一次,oneshot 读一次电压（程序查询/定时采样）
  → button 组件对电压序列做去抖 + 判定（按下/单击/长按/双击）
  → 回调 cb_click/cb_long 被调用
  → BSP 幽灵锁过滤 → 发到 main.c on_key
  → on_key 加 LVGL 锁 → 更新 UI / 进子应用
```
**408 对照**：
- 这是"**程序查询方式 + 定时中断节拍**"结合：CPU 不是干等按键（那叫程序查询空转），而是被**定时中断**唤醒去"轮询一次 ADC"
- 中断服务（ISR）里**只做最短的事**（读数/置标志），把重的判定丢给任务线程——"ISR 要短"的经典准则
- **硬件消抖 vs 软件消抖**：机械抖动导致电压在多个档位间抖动 → 用采样序列 + 时间窗（250ms 幽灵锁）判定，是"信号 + 时序"的滤波
- **CPU 响应中断的条件**：中断使能 + 中断优先级 → 才进入现场保护（压栈 PC、PSW）→ 查中断向量表 → 执行 ISR → 恢复现场返回。本项目从"电压变"到"on_key 改 UI"就是完整现场切换

## 1.6 总线（外设 I/O 的载体）
| 总线 | 线数/时钟 | 全双工? | 用途 | 考点 |
|---|---|---|---|---|
| I2S | 4, 同步(BCLK/WS) | 是(有DX/RX) | 数字音频传 ES8311 | 时钟分频 MCLK=256×fs=4.096MHz |
| SPI | 4+, 同步 | 是 | LCD 屏 | CS 片选/D/C 命令数据 |
| I2C | 2, 同步 | 半双工 | 扫描/传感器 | 地址寻址、一条主线上多设备 |
| GPIO | n, 异步电平 | — | 背光/功放使能 | 简单 I/O |
- **考点**：串行 vs 并行；同步（有独立时钟线）vs 异步（UART 靠波特率对时）；总线仲裁（I2C 从机地址应答）

## 1.7 I/O 系统（★"文件IO流"之另一半 + 中断驱动 I/O）

### 1.7.1 三种 I/O 控制方式（408 大题重灾区）
| 方式 | CPU 参与 | 特点 | 本项目对齐 |
|---|---|---|---|
| 程序查询 | 全程查状态位、忙等 | 简单但占 CPU | 按键 ADC 单次 read（低频率可接受） |
| 中断驱动 | 设备就绪才中断 CPU | 提高利用率 | 定时器中断采样、I2S/DMA 触发 |
| DMA | CPU 只给首末，数据由 DMA 搬 | 最快、不占 CPU 搬数据 | **I2S 音频用 `dma_desc_num=6,dma_frame_num=240` 硬件 DMA 搬运** |

### 1.7.2 块设备与 Flash 的底层（读写文件最终落到这）
- SPI Flash 是**块/页设备**：最小写单元是**页（Page）**，擦除单元是**扇区（Sector）**，且**写前必须擦**（写 1→0 可，0→1 必须先擦）
- SPIFFS 把分区（如 `recordings` 那块 3MB 区）划分成块，管理"哪些页被占用、哪些空闲、哪些待擦除"。`fwrite` 最终变成"把页缓冲写回 Flash 页 + 更新映射表"
- **考点映射**：
  - 文件正文在**磁盘/闪存→内存**之间搬运 = 上一篇 §1.3 存储层次 + 本篇 I/O（DMA）协同
  - 这就是计组"**块设备的 I/O 以块为单位**、写放大、擦写次数寿命"，以及 OS"缓冲区、page cache"的硬件基础

# 第二部分　操作系统

> 对应 408《操作系统》大纲。下面是"任务/内存/文件/IO/同步"全在本项目落地。

## 2.1 概述
- **OS 功能**：处理器（任务调度）、内存（堆/栈管理）、文件（SPIFFS）、设备（驱动）、网络（LwIP）、用户接口（LVGL）——本项目都有
- **中断贯穿**：OS 靠中断实现调度、I/O、时钟

## 2.2 进程与线程（FreeRTOS 任务）
- 任务是**线程**（同进程共享地址空间的并发执行流），每个任务一个 **TCB + 私有栈**
- 本项目真实任务：`rec_cap`(录音)、`rec_play`(回放)、按键任务、LVGL 刷新、`voice_worker`、WiFi 事件、`wifi_apply`、诊断任务
- **三态**：就绪/运行/阻塞。`vTaskDelay(pdMS_TO_TICKS(30))`=阻塞让出 CPU；等待事件/锁=阻塞
- **上下文切换**：`sched_yield` 或系统节拍发生，保存当前任务寄存器 → 恢复下一任务。20143-20145 的"现场切换"在每次按键/录音/网络里高频发生

## 2.3 处理机调度
- RTOS 用**优先级抢占 + 时间片**：`REC_PRIO=5`，高优先级就绪即抢占；同优先级轮转
- **优先级倒置/反转**（常考）：低优任务持锁阻塞高优任务 → 本项目用"互斥量 MUTEX 自带优先级继承"规避（LVGL 锁）
- 比较篇：批处理（先来先服务）vs 交互/实时调度（本 RTOS）

## 2.4 同步与互斥（并发三大问题）
- **临界区**：`bsp_lvgl_lock(100)/unlock`——所有任务改屏幕前加锁。互斥，一次一个任务进
- **信号量/互斥量**：LVGL 锁即互斥量
- **生产者-消费者**：按键/WiFi/录音"产生事件" → 环形队列（§3.1）→ UI"消费"；队列 + 队列长度 8（有界 → 满则丢/覆盖，避免无限等待）
- **`volatile`**：`static volatile bool s_recording` 保证多任务读到最新内存值（防编译器优化缓存到寄存器）
- **原子性问题**：`s_evt_w` 的读-改-写非原子；若被 ISR 打断可能丢事件。规模小可接受；大则要用关中断/无锁 CAS

## 2.5 死锁
- **四条件**：互斥 / 占有等待 / 不可剥夺 / 循环等待（背）
- **本项目预防**：锁一律**带超时**（`bsp_lvgl_lock(100)` 超时返回 false），不会无限等 → 破坏"不可剥夺/循环等待";锁定期间只做最短操作再解锁
- 调试法宝：崩溃日志里 `s_cap_task` 句柄非空、`recording=1` 却无人解锁 → 可推"疑似死锁/阻塞"独占（本段是排查思路）

## 2.6 内存管理（★16kHz 崩根：连续块 vs 总和）
- **分区 vs 页 vs 段**：
  - 分区表 = **静态固定分区**（编译期定地址大小）
  - 堆分配 = 可变分区 + **首次/最佳适配**，产生**外部碎片**；`esp_get_free_heap_size()`(总空闲) vs `heap_caps_get_largest_free_block()`(**最大连续块**) 之差 = 碎片量
- **本项目血泪**：总空闲 33KB，最大连续只有 16KB → `xTaskCreate(…, 32KB)` 要一整块 32KB 连续内存 → **pdFAIL**；编码器状态也因无连续块无法分配 → PANIC。→ "内存是"总和 vs 连续"两维"考点
- **栈管理**：每任务独立栈，栈向下增长；`uxTaskGetStackHighWaterMark()` 看剩余底=HWM（HWM≈0 = 栈快满 → 溢出风险）
- **地址转换**：分区/堆是直接地址；若用 MMU 则是页表转换——本项目无虚拟内存（裸机），对照理解即可

## 2.7 文件管理（★"文件IO流"之OS视角 + 可靠写入）
- **文件系统 SPIFFS**（装在 `voicepack`/`recordings` 分区），标准 POSIX 文件 API：
  ```c
  fopen(ACTIVE_TMP,"wb") → fwrite(帧) 循环 → rename(ACTIVE_TMP, "/rec/R%07u.FRC")
  ```
- **考点全命中**：
  - **命名**：`R%07u` 文件名补零 → 字典序=时间序，利于遍历排序
  - **目录**：`opendir/readdir/dirent` 遍历录音列表（文件管理目录项）
  - **原子提交**：写完先存**临时文件** `ACTIVE.TMP`，最后 `rename`（原子改名）才可见 → "崩溃前文件不完整，改名后才是正式文件"。这是文件系统**一致性/事务**思想
  - **缓冲**：`fwrite` 有用户缓冲 + SPIFFS 页缓冲，量大才落盘 → 匹配"文件缓冲区"考点
  - **容量配额**：`study_recorder_free_kb()<100KB` 拒绝继续录 → 提前防写满
- **文件与I/O结合**：文件底层读写在 §1.7 详述（块设备+闪存页）

## 2.8 设备管理
- 设备独立性与驱动层：`bsp_*` 把硬件封装成接口，app 不直接碰寄存器 → "设备独立性/统一接口"
- **中断驱动的 I/O**：§1.7 的 DMA/中断在此作为 OS 设备驱动实现
- **NVS 键值存储**：类似**小型数据库**——命名空间=表、键=主键、`nvs_commit`=**事务提交**（落盘方式有损原子保证，断电不丢半条）；键值底层是 Flash 上的索引分配

## 2.9 （嵌入式专属）复位 / 崩溃恢复 / 低功耗
- `esp_reset_reason()`：`ESP_RST_PANIC`=内核异常重启 / `POWERON` / `SW`
- **崩溃恢复**：上次若 PANIC，启动时清残留 `ACTIVE.TMP`、从 NVS 恢复序号 `seq` —— "检查点 + 从持久态恢复"
- 低功耗睡眠：`esp_sleep_get_wakeup_cause()` 判断从哪种唤醒（深度睡眠/定时器唤醒）

# 第三部分　数据结构

> 对应 408《数据结构》。真实代码里的结构，别背抽象的。

## 3.1 线性结构
### 环形队列（循环队列）—— 事件缓冲 ★
```c
#define EVT_N 8
static int s_evt[EVT_N], s_evt_w=0, s_evt_r=0;
push: s_evt[s_evt_w]=e; s_evt_w=(s_evt_w+1)%EVT_N; 满则(r+1)%EVT_N覆盖最旧
poll: if(r==w)空; e=s_evt[r]; s_evt_r=(s_evt_r+1)%EVT_N;
```
- **FIFO**，头尾指针循环推进；判空 `r==w`；取模回绕
- 408 直接考：循环队列判空判满、`(rear+1)%size==front` 判满、"牺牲一格 / 预留标志 / 计数"三种判满法。这里是"满则丢最旧"（覆盖策略变体）
- 同样用于**诊断日志环形缓冲**（崩溃前每秒一条，不丢最近）

### 顺序表/定长数组 —— 任务列表
- `study_task_t[256]`（`TASK_MAX_COUNT`），`title[40]`——**顺序存储**，定长因内存有限
- 操作：`list_today` 遍历筛选 + 排序；`add/get/delete` = 顺序表增删查

## 3.2 位图
- `repeat`：`STUDY_REPEAT_CUSTOM` 用 `bit0~bit6` 表周一..周日——**一字节存一周**，`&/|` 判星期，空间效率满分
- "今日已响铃" fire 位图：避免重复提醒，`set/clear/test`

## 3.3 树与图
- **分类树**：科目(category) → 子分类(subtype) → 任务(task) = 一棵**多级树**，查找/筛选=树的遍历
- **调度器查询**：从任务集合中"找下一个到点且未响铃"= 线性扫描；可优化为 **最小堆/有序双向链表**（讲清为何当前规模遍历即可）

## 3.4 函数指针表 vtable = 多态（接口抽象）★
```c
typedef struct { int (*save)(..); int (*load)(..); /* … */ } study_task_store_t;
```
- **函数指针数组 = 虚函数表 vtable**：C 语言的多态
- 同一业务可配 `study_task_nvs.c`（真机）或内存 mock（`tests/` 宿主测试）——**依赖注入 / 抽象接口**
- 映射：数据结构"抽象数据类型(ADT)" + 编译原理"间接调用"

## 3.5 哈希
- NVS = 键-值，底层把键做**哈希索引**分配到 Flash 槽位；`nvs_open("wifi"/"recorder"/"tasks")` 命名空间
- 冲突与装载因子概念在此有真实承载

## 3.6 排序 / 查找
- 录音列表按文件名/`seq` 排序：因命名 `R%07u` 字典序=数值序，`readdir` 后按需排序
- 任务"有时间的升序在前、无时间在后" = 排序规则（key 自定义）

## 3.7 结构体对齐与内存（计组/数据结构交叉）
- 结构体字段间**内存对齐**插入 padding：`study_task_t` 里 `int` + `int8_t` 排布影响 `sizeof`
- 嵌入式常**按字段大小降序排**省空间；未对齐地址→RV32 可能异常(PANIC 一源)

## 3.8 字符串
- C 字符串`\0`结尾；`snprintf` 安全格式化（补零`%07u`字典序技巧）；"字符串=指针+长度约定"，防 `strcpy` 溢出用有界 `strncpy/snprintf`

# 第四部分　计算机网络

> 对应 408《计算机网络》。本项目是"让一台只有 3 键的机器配网 + 下载录音"的网络小系统。

## 4.1 概述与分层（五层模型）
LwIP 协议栈自底向上：物理(802.11) → 链路(WiFi MAC) → 网(IP/ICMP) → 传输(TCP/UDP) → 应用(HTTP/DHCP/SNTP)。封装数据逐层加头。（常考封装/解封装图）

## 4.2 物理层 & 数据链路层（WiFi 无线）
- 802.11 2.4GHz，DSSS/OFDM 调制；**CSMA/CA** 载波侦听避碰（无线非同发生碰撞侦测，用随机退避）
- MAC 地址：SSID 自动拼 **后4位MAC**（唯一标识设备热点）
- **WPA2-PSK**：配对加密，`WIFI_AUTH_WPA2_PSK`；密码 **≥8 位**（协议强制的预共享密钥长度下限）→ 计网安全考点

## 4.3 网络层（IP/子网/DHCP）
- **子网**：SoftAP 用 `192.168.4.x/24`，设备自己固定拿 `.1`（网关）。手机连上后同网段即可互访
- **DHCP**：设备做 STA 连路由器后，向 `255.255.255.255` 广播请求 → 路由器分配 IP/网关/DNS（UDP 67/68）；设备做 AP 时自己当 DHCP server 给手机发 `192.168.4.x`
- 其实就是"两套接口两张网卡两种 IP"（见 §6 专题）

## 4.4 传输层（TCP/UDP）
- **TCP**：面向连接、可靠、顺序、流量/拥塞控制——HTTP（配网、下载）走它
- **UDP**：无连接、不可靠、开销小——DHCP、SNTP 走它
- **三次握手/四次挥手**：设备 httpd 与手机浏览器每次连接都发生（测试时可打日志观察）
- **端口**：HTTP 固定 `80`（`STUDY_WIFI_AP_PORT`）；DHCP 67/68；SNTP 123

## 4.5 应用层
### HTTP 网页配网
- 设备起 httpd（Server），注册路由：`GET /`(配网页)、`POST /save`(收 WiFi 账号密码)
- 手机浏览器是 **Client**：GET 首页 → 填表 → POST `/save`，`application/x-www-form-urlencoded`，`ssid=...&pass=...`
- 设备 `parse_form` 解析 + `url_decode`（`%xx` 十六进、`+`→空格）→ 存 NVS → 连家里 WiFi
### HTTP 录音列表/下载（★"手机下载录音"之一半）
- 路由：`GET /rec/list`(录音列表页)、`GET /rec/dl?seq=N`(下载 WAV)、`GET /rec/del?seq=N`(删除)
- **查询串 query string**：`?seq=0123456` 从 URL 解析参数（`httpd_query_key_value`）
- **响应**：`Content-Type: audio/wav`、`Content-Disposition: attachment; filename=R….wav`（弹"文件另存为"）
- **分块传输 chunked**：`httpd_resp_send_chunk` 逐段发（先 44B WAV 头，再循环发解码 PCM）——"流式响应，不必知道总长也能开始传"
### SNTP 校时
- 设备连上网后向 NTP 服务器同步 UTC → 转本地时间显示"几点"。`SNTP over UDP:123`——计网"网络时间协议"
### DNS
- 若域名访问需解析 `域名→IP`（UDP 53）；本项目多用 IP 直连

# 第 6 章　四个专题（★ 重点，逐字节讲）

## 专题 A：文件输入输出流 —— 从 `fwrite` 到闪存页的完整征程

**你问的正是计组 §1.7 + OS §2.7 的合流。逐层拆：**

```
应用层  study_frc_enc_frame → fwrite(帧数据, 写 ACTIVE.TMP)
        ↑ 这只是"C 库函数", 并没真的碰硬件
───────────────────────────────
C库     libc stdio: 把数据先放"用户缓冲", 满了/fflush 再调 OS 写系统调用
───────────────────────────────
OS     系统调用 open/write → SPIFFS 驱动
        · 把文件逻辑地址换算成"分区内块(b)号 → 块内页偏移"
        · 找到空闲页, 准备"载入要改的整页"（闪存无法部分擦写）
───────────────────────────────
驱动    flash 写 API: 若目标页已写脏 → 先 ERASE 一页(0→1), 再 PROGRAM(按需写1/0)
        · 这是计组"块设备以块真-写"的分页/擦写本质
───────────────────────────────
硬件    数据经 SPI 总线写入 Flash 页; 量大时可用 DMA 搬运, 不占 CPU
```

**计组考点提炼**：
1. **三级 I/O**：为什么音频录/播用 **DMA**（I2S↔SRAM 不占 CPU），而按键这种低频用**程序查询/定时中断**——不同速率用不同 I/O 方式
2. **块设备的写放大/擦写**：页是写单元、扇区是擦单元，写前必擦。所以 SPIFFS 会"搬空页再擦整扇"→ 有寿命/性能权衡
3. **缓冲（Buffer）**：C 库缓冲 + SPIFFS 页缓冲做了俩级缓冲，避免每字节都跨总线——"缓冲区"同时是计组(流水线缓和)和 OS(文件系统)考点
4. **数据表示**：WAV/FRC 里 `u16LE` 端序、int16 补码，在第 1.2 已有
5. **崩溃一致性**：`rename` 原子提交（OS 2.7）本质是"让数据的可见性在某一原子点发生" → 呼应计组"外部不可见中间态"

> 一句话：**`fwrite` 只是加法，真正"写进"是靠驱动做"擦-写页"，再由 DMA/中断与内存交换。**

## 专题 B：点击按钮触发中断的完整链路

408 中断大题要把"从物理到寄存器的现场"讲全。本项目拆给你：

```
1 触发源   物理按键按下 → 电阻分压 → ADC1_CH 电压变化
2 采样     硬件定时器中断(TIMER) 周期性触发, ISR 只读一次 ADC 原始值(极短)
           → 这就是"程序查询驱动的 I/O + 定时中断节拍" (1.5.2)
3 判定     线程里对连续电压序列去抖: 低于阈值+持续≥80ms=按下, ≥500ms=长按
           → 一个时序/有限状态机
4 事件     判定结果 → 回调 on_event(BTN/prESS...) → 幽灵锁过滤 → on_key
5 加锁     bsp_lvgl_lock(100)：进入"临界区", 不让其他任务同时动屏幕
6 作用     更新菜单/进子应用/发录音命令; 完事后 unlock
```

**408 考点对照（中断 I/O 流程）**：
- **中断请求→响应→服务→返回**：请求来自定时器/ADC；响应要**关中断+保护现场(压栈 PC/PSW)**；服务在 ISR 内做最少事；返回恢复现场
- **为什么 ISR 短**：ISR 里放长逻辑会让其他中断排队、拖慢系统——本项目把"重活"（去抖、改 UI）放线程回调，而 ISR/定时回调只读采样
- **中断 vs 异常**：按键中断是**外部异步 I/O 中断**；而"读非法地址导致 PANIC"是**内部 ETRAP（异常）**——两者都走异常/中断响应机制，这也解释了为什么 16k 崩溃会 PANIC 重启
- **中断优先级/屏蔽**：只要有中断使能位，按 优先级 决定先响应谁；关键临界区（如改 s_evt 指针）最好关中断保证原子
- **程序查询 vs 中断**（本专题主考点）：CPU 空闲时若"每帧都机器枪轮询 ADC"就叫程序查询；这里是用**定时中断去轮询**,把 CPU 空出来做别的事

## 专题 C：为什么"手机连上设备WiFi、填家里WiFi密码, 设备就能上网"

**⚠️ 重要纠正**：设备**不是借手机转发流量**。真实原理（看代码 `wifi_start_apsta` + `on_ip_event`）：

```
┌──────────── 路由器(家里) ────────────┐
│  2.4GHz, SSID="家里WiFi"             │
└──────┬───────────────────────────┬──┘
       │ STA(设备连路由器)          │ STA(手机连路由器,平时)
   ┌───┴───────┐            ┌─────┴────┐
   │ ESP32-C3  │            │   手机    │
   │ 模式=APSTA│            └──────────┘
   └───┬───────┘
   AP口(自己热点 192.168.4.x)
       │ 手机连设备热点时, 手机多了一张192.168.4.x的网卡
```

**流程**（`study_wifi_init → wifi_start_apsta`）：
1. 设备设 `WIFI_MODE_APSTA`：**hotspot(AP) 与 station(STA) 同时开**。AP 管设备自己的热点（`STU_xxxx`/密码），STA 管"去连哪个路由器"
2. 无凭证 → 只开 AP；你手机连它，浏览器 `192.168.4.1` → `POST /save` 交家里 WiFi 账号密码
3. 设备 `creds_save` 写 NVS → 起独立任务 `apply_creds_task` → `connect_sta`
4. `esp_wifi_connect()` 用 STA 口真正去连你家路由器 → 路由器 DHCP 给设备发 IP → **`IP_EVENT_STA_GOT_IP` 事件** → 设备"已联网"
5. 从此设备自己的 STA 直连路由器，能上网（下载/校时），与"手机是否还连着"无关

**计网考点**：
- **两种角色**：同一芯片可同时是 **AP(接入点) + STA(站点)** 双星拓扑（APSTA）——映射"主机可以同时有多个网络接口"
- **DHCP 双向**：设备作 STA 时向路由器**租 IP**；作 AP 时给手机**分配 192.168.4.x**
- **网关/子网**：`192.168.4.1` 是 AP 接口的 IP → 手机浏览器把目标包发给网关，选路到设备 = 同一子网直连
- **配置持久化**：账号密码存 NVS，下次开机自动走 STA 连接（"有凭证自动连"）
- **故障回退**：连不上 → 超 `WIFI_MAX_RETRY` → 自动重开 AP 配网页（可用性/状态机）
- 一次"看起来跨设备"的过程，本质是**设备自己完成"STA 连路由器"**，手机只是**引导配置**（配网手段），不是数据中继

## 专题 D：为什么手机能下载设备里的录音文件

**核心事实**：**设备就是一台 HTTP 服务器（Web Server），手机是浏览器（Client）**。设备并不"把文件发给路由器"，而是你在浏览器里 GET 一个 URL，设备把数据直接回给你。

```
手机浏览器  GET http://192.168.4.1/rec/dl?seq=1234567
   │  ↑ 192.168.4.1 = 设备 AP 接口 IP (手机连设备热点时同网段)
   ▼
设备 httpd 处理 handle_rec_dl:
   1) 解析 ?seq → 找到一个录音  path=/rec/R0000123.FRC
   2) study_frc_open 打开(SPIFFS读)
   3) 内存里构造 44 字节 WAV 头(RIFF/WAVE/fmt/data, 全小端)
   4) 循环 study_frc_read_pcm 解码成 int16 PCM
        httpd_resp_send_chunk(pcm) 分块发出
   5) 发完 chunk(NULL,0) 结束
   ↓
手机浏览器收流 → 按 Content-Disposition 存成 R….wav
```

**计网考点（这是一道大题素材）**：
- **HTTP 请求/响应**：`GET /rec/dl?seq=N`，状态码（200/400/404），`Content-Type`、`Content-Disposition` 头
- **Query String**：`?seq=N` 从 URL 解析参数
- **流式/分块传输**（`Transfer-Encoding`/chunked）：**不必等整文件生成**，边解码边发 → 手机端边收边播放。这就是"流"——之前"文件IO流"在网络侧的行为
- **C/S 架构**：设备起 listen socket（**服务器**），手机 connect（**客户端**）；一个 Server 服务多个手机(`max_connection=4`)
- **CSMA/CA + 802.11**：无线信道共享，两者同热点 UHF 时避开冲突才能收数据

**多科目串起来（本题最能体现 408 融会贯通）**：
- 数据结构：WAV 头是**定长结构体**内存布局(§3.7)，PCM 是 int16 数组
- 计组：数据从 Flash 页 → 内存 → 经 DMA/中断 + CPU 编码 → 送网卡（DIO）
- 操作系统：`httpd` 解码线程跑在一个任务/栈上（HTTPD 配置 `stack_size=8192`），大量解码用栈；文件读取经过 SPIFFS 缓冲
- 计网：上述 HTTP/TCP/UDP/IP/链路全线

> 一句话：**"手机下载录音" = 设备当 Web 服务器，把 FRC 压缩音频边解码成 WAV 边通过 HTTP 流给你；"手机配网" = 设备用 AP 给手机一个临时网页，手机把路由器的账号密码反着喂给设备的 STA。**

# 第 7 章　重点案例：16kHz 录音内存崩溃复盘（综合分析）

**现象**：切 16kHz Speex 宽带 → 第二条"rec error"、>10 秒闪退、多段后闪退。
**根因**（贯穿计组/OS）：
1. **内存需求翻倍**：8k→16k 帧样本 `160→320`；WB 比 NB 多了 MDCT/FFT/心理声学 → 栈+堆大增
2. **连续块不足**：空闲堆≈33KB，`最大连续块`≈16KB；`xTaskCreate(rec_cap, 32KB)` 要一块 32KB 连续内存 → `pdFAIL`；即使建任务，剩余堆装不下 WB 编码器 → `speex_encoder_init` 返回 NULL
3. **崩溃类型**：分配失败 / 栈溢出 → 内存踩踏 → CPU 异常(ETRAP) → `ESP_RST_PANIC` 重启
4. **为什么"短短可、长短崩"**：长录音随时间分配累积、旧块未回收 → 在某刻碎片/耗尽 → 突崩

**解法（都对应正课考点）**：
- 编码回退 8kHz Speex NB（改宏 `STUDY_REC_SPEEX`+`)
- 压缩任务栈 `CAP_STACK_BYTES 32K→16K`（-ffunction-sections 不在 WB 码本, 减小常量段）
- **防溢出门槛**：录前 `esp_get_free_heap_size()<8000` 拒绝、`study_recorder_free_kb()<100KB` 拒绝（这是"防御式容量检查"）
- **失败路径回到 SDK**：任务创建/编码失败必须打日志并安全退出（不残留 ACTIVE.TMP）

## 结语
一台只值几十块的 ESP32-C3 小玩具，装进了 408 几乎全部考点：
- **计组**：地址映射、块设备 I/O、中断响应、大小端、定点数、DMA

- **计网**：五层、WiFi/DHCP/HTTP/TCP/UDP/SNTP、C/S 与流式传输

尤其你关心的三件事得到答案：
- 文件输入输出流 → **缓存、块擦写、DMA、缓冲**（计组 I/O 章节）
- 点击按钮触发中断 → **定时采集 + 中断响应 + ISR 短 + 现场切换**
- 配网与下载 → 设备 **APSTA 自己连家里 Wi-Fi；设备当 HTTP 服务器把录音流给你**
